# Durable private acquisition scheduling

`./scheduler` exports `AcquisitionScheduler`, using the pinned Evidence persistence SDK on a dedicated discovery operational database. Never connect it to another engine's operational database. Apply the SDK migration with a privileged migration identity; the runtime driver must use a separate restricted login granted the runtime role. A trusted host authenticates Context, derives its clock/purpose and owns the Database and mandatory outcome-verifier implementation. Diagnostic strings, source policies and lease tokens are not authentication. There is no raw HTTP endpoint or built-in worker daemon.

A listed human owner creates an explicitly bounded collection. Listed service/agent workers with `discovery:acquire` may lease one due item with an exact expected revision. A lease records the actor, attempt, token and deadline. Leasing is idempotent for lost acknowledgements, but replayed lease metadata grants no execution authority. A separate `consume` transaction changes that lease to running before returning its work description. Consumption is deliberately one-shot: a lost commit acknowledgement requires loading/reconciling state, never repeating I/O on a replayed permit. The host worker must honor these semantics, run the approved capture boundary and quarantine captured bytes.

The scheduler commits collection revisions, audit history and minimal change outbox events transactionally. A completion needs a mandatory verified durable receipt for the exact capture or no-capture outcome. There is no permissive verifier default. The verifier is bounded, receives cancellation and must return exactly true; provider diagnostics are redacted. Receipt references retain their exact kind/ID/revision in the lease, and byte digests/coverage remain in the collection attempt. Only metadata is stored here; captured bytes belong in the evidence engine. Completed attempts do not inflate unique-edition counts.

Expired unconsumed leases become explicit failures because no work description was issued. Expired consumed leases become `reconcile`, keep their attempt started and continue occupying concurrency capacity. They are never automatically retried. The original worker or a listed human owner can resolve them through a verified capture/no-capture receipt. Human pause prevents new leasing and consumption; it cannot recall already consumed work, and completion/reconciliation remains possible while paused. Failed attempts retain the collection refresh cooldown. The state supports up to 1000 items and 10000 retained attempts per collection; archive/rollover requires future host tooling rather than silent history deletion.

The verifier must bind its receipt to the supplied scope, collection/attempt/item, policy, URL, purpose, acquisition key, outcome, exact capture metadata/byte count/source digest (or failure code), and receipt kind/ID/revision. It is a trusted integration boundary and must consult durable upstream state, not accept caller strings as proof. Receipt verification is a bounded observation; this adapter does not claim distributed atomic permission fencing or revocation across services. Deployment transaction timeouts and cancellation must accommodate its bounded verifier. A noncooperating verifier is not forcibly terminated, so deployment resource bounds still apply.

Tests execute real migrations, restricted runtime roles, transactional commands, competing revisions, audit/outbox, loss after commit, rollback and a filesystem-backed database reopen. PGlite does not establish independent wire-session contention, runtime network login setup, deployed worker correctness, crash recovery against a real evidence service, or live qualification. No scheduled host process, catalog crawler, outbound mail, publication or real research import is started by this library.

## Receipt deadline admission and result fencing

The scheduler's receipt verifier now checks a monotonic deadline before copying/calling a verifier and after its result, in addition to the cancellation timer. Owned signals close on success, rejection, timeout and error; strict true is still required and callback diagnostics remain sanitized. A blocked JavaScript callback cannot return late authority before a delayed timer runs. This bounds acceptance, not callback execution or already begun SQL: synchronous JavaScript cannot be preempted and callback effects cannot be undone.

## Explicit current-clock consumption

`consumeCurrent(context, collectionId, expectedRevision, token, clock)` requires a trusted synchronous live clock. It acquires the existing owning-project lock through a checked audit BEFORE reading stored schedule state, then samples the clock AFTER that read. Malformed, throwing or request-time-regressed clock values fail closed with sanitized diagnostics. Stored policy expiry, lease expiry/ownership, pause and revision checks use that sampled time. This is one-shot consumption, with the same commit-before-work and unknown-acknowledgement discipline; it performs no acquisition I/O.

The original four-argument `consume` remains compatible and still uses caller-supplied Context.now. Both consumption paths now acquire the project lock before the admission read. The checked audit uses the captured request Context time; it is not a fabricated live consumption timestamp. No record schemas, identifiers, fingerprints, persistence pin or shared contracts change. Other scheduler operations still use captured caller time. Hosts should explicitly select consumeCurrent for current-clock admission, maintain current authenticated roles/configuration and enforce runtime policy immediately before outbound I/O. This observation is not a transferable permit or distributed revocation fence.

Four new canonical-migration/restricted-authenticated PGlite groups cover clock advancement after an observed actual locked SQL read, stored source-policy expiry, one-shot/lost post-COMMIT acknowledgement and captured context, and missing/malformed/regressed/throwing clocks. The SQL timing hook is embedded instrumentation, NOT independent network-session blocking. No new PostgreSQL-session, deployed clock/receipt/worker/liveness, listening host or production qualification is claimed. The trusted synchronous clock is not forcibly preempted; begun SQL is awaited. Rejected consumption leaves the lease available only to a later freshly authorized, unexpired call; absence of a receipt is never proof of absent output. No retry, daemon, provider send or publication route is added.
